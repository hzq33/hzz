# 结构化检索接入设计 v3 — LLM 后处理 + 角色知识边界

> 日期：2026-08-10 · 状态：待评审
> v1 错误：把 LLM 摘要（时间线 summary/关系 summary/设定书 content）当事实注入 → 污染上下文。
> v2 修正：结构化数据只做原文索引（沿 evidence/block_id 取原文），不注入摘要。
> v3 采纳用户 5 点意见重构：**LLM 后处理（检验相关性+补标注+知识边界）+ 先验证后改 + 复用现有通道**。

---

## 1. 用户 5 点意见 → 设计结论

| # | 意见 | 设计结论 |
|---|------|---------|
| 1 | 这是新检索通道吗 | **不另起炉灶**：结构化数据（时间线/关系/设定书）**不参与召回**，只作为 LLM 后处理的**参考输入**。召回仍走现有四通道。通道数量不变 |
| 2 | 先验证效果再改 | **先跑基线**（eval_dialogue 52 case），量化现状 relationship 意图（20/52=38%）检索效果；改后对比同评估集。见 §6 |
| 3 | 上下文太少难精准匹配 | **匹配交给 LLM + 会话上下文**：LLM 后处理能看到 完整对话历史+角色+引用锚点，判断"后来"指什么、"他"是谁；不用 query 单句硬匹配 |
| 4 | 信息交 LLM 处理 + 角色知识边界 | **LLM 后处理决策"该不该答"**：角色只能知道与自己相关/听说的；检索到但角色不该知道 → 不注入/标记不可答 |
| 5 | RAG 原文再经 LLM 处理 | **核心机制**：向量召回原文 → LLM 一次后处理 = 相关性检验 + 时间/关系标注 + 知识边界判断 |

## 2. 目标架构（v3）

```
用户输入 + 会话上下文（历史/角色/引用锚点）
        │
        ▼
[向量检索] 现有 search_raw（四通道，通道数不变）
        │
        ▼ 召回原文片段（带 block_id/source/channel/score）
        │
[LLM 后处理] ← 新增，核心（1 次 LLM 调用，批量处理全部片段）
        输入：召回原文片段 + 结构化参考（时间线/关系图/设定书，只读）
        输出：{保留片段[], 标注[], 知识边界判定, 是否可答}
        1. 相关性检验：每个片段是否真正回答用户问题（过滤噪声召回）
        2. 结构化标注：片段发生在什么时间（era/seq）、涉及谁的关系
           → 标注来自结构化数据，但只作"参考注记"不作文本主体
        3. 知识边界：扮演角色是否知道这件事（自己经历/听说/不该知道）
           → 不知道的片段标记 not_known，不注入或提示角色拒绝
        │
        ▼
[注入 messages] 保留片段 + 标注（角色可答的部分）
```

**关键变化 vs v2**：
- 结构化数据**不参与检索**（不召回），只给 LLM 后处理当"参考字典"——彻底避免"新通道"
- 匹配/召回完全交给 LLM（泛化，处理"后来呢/他"这类依赖上下文的查询）
- 新增**知识边界**：检索到 ≠ 该答（角色视角过滤）
- 一次 LLM 后处理 = 相关性验证 + 标注 + 边界判断，三合一

## 3. LLM 后处理设计

### 3.1 输入组装

```
[系统] 你是 {角色} 的检索精炼助手。
任务：对检索到的原文片段，判断：
  1) 每个片段是否与用户问题相关（保留/丢弃）
  2) 片段的时间与关系背景（参考结构化数据注记，不杜撰）
  3) 作为 {角色}，你【亲身经历/听说过/不该知道】哪类信息
       - 亲身经历 → 可直接回答
       - 听说过 → 可回答但注明来源（"我听说…"）
       - 不该知道 → 不注入，角色应表示不知道
  输出 JSON: {kept: [{block_id, note, knowledge: own|heard|unknown}], answerable: bool}

[结构化参考]（只读，缺失则跳过）
  - 时间线: chronicle 事件摘要（seq/era/角色/章节）——仅供定位标注
  - 关系: A-B relation 记录（type/polarity/章节）
  - 设定书: entity 条目（seq 范围）
  注：参考数据为 LLM 二度摘要，**禁止直接输出其内容**，只允许用它标注时间/关系

[召回原文] block_id + 文本片段 × N（cap 8）
[用户问题] {query}
```

### 3.2 输出消费

- `kept[]`：只注入保留片段的原文文本（带 note 标注如"第2章·转生后"）
- `answerable=false`（角色视角不可答）→ 注入 `_NO_FACT_HINT`（"作为{角色}，这件事我并不知道"），
  不注入原文——**检索到了但角色不该知道，就不答**
- 标注（note）只作一行定位注记，原文文本是事实主体

### 3.3 成本控制

- 一次 LLM 调用/回合（批量处理全部片段，非逐片段）
- 无召回（hits 空）→ 不调用
- 结构化参考缺失 → 正常调用（相关性检验+知识边界仍有效）
- 预估 +1 次 LLM/扮演回合；通用 chat 可配开关（默认关或复用）

## 5. 实施步骤

### 阶段 0：基线验证（先做，不改代码）
- 跑 eval_dialogue 52 case → 记录 relationship 意图（20 case）的现状命中率
- 结论：如果 relationship 意图命中率已高 → 问题不大；如果低 → 后处理价值确认

### 阶段 1：LLM 后处理（扮演链路）
- 新增 `post_retrieval_refine()`（application 层，输入 hits+结构化参考+角色 → 输出 kept/标注/边界）
- chat.py `_build_user_messages` 接入：fact_text → refine → 注入
- 结构化参考读取：timeline/lorebook/relation 的只读封装（services 已有 load_*）
- 测试：相关性过滤（无关片段被丢）、标注（时间/关系注记）、知识边界（他人私事 → 不注入）

### 阶段 2：通用 chat 接入（可选）
- search 工具链同样接后处理（角色=通用读者，无知识边界，只做相关性+标注）
- 默认关（成本），配置开

### 阶段 3：评估对比
- 同评估集重跑 → 对比 baseline（尤其 relationship 意图命中率变化）
- 新增时间类 case 到评估集（现状 0 个，补"后来/第X卷/转生前"类）
